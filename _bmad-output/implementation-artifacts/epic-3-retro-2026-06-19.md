### 🟡 Issue 2: `_id`/`id` Pydantic v2 serialization-alias pattern — DOCUMENTED AT RETRO

**Found in:** Story 3.2 debug log (`ReplacementRuleResponse.id` serializing as `_id`)

**Problem:** `MongoBaseModel` declares `id: str = Field(alias="_id")`. In Pydantic v2,
`alias` controls **parsing** only — not serialization. A subclass inheriting this
field and calling `model_dump(by_alias=True)` emits `{"_id": ...}` in the JSON
response, not `{"id": ...}`. The fix required redeclaring `id` with both
`validation_alias="_id"` and `serialization_alias="id"` in the subclass.

Additionally, adding a duplicate `@field_validator("id")` in a subclass raises a
`PydanticUserError: duplicate validator` at import time — a non-obvious error.

**Fix applied:**
- `MongoBaseModel` docstring upgraded to the definitive pattern guide
- Two patterns documented: Pattern A (alias-only subclass) and Pattern B (subclass
  with extra `@field_validator` on a different field)
- Three common mistakes listed with explicit DO NOT warnings
- `from_entity()` classmethod contract documented (always pass `"_id"` key)

**File changed:**
- `forward-bot/src/forward_bot/api/schemas/base.py` — `MongoBaseModel` docstring

**Applicable to all future response schemas (Epic 4 `MessageMappingResponse`,
Epic 5 log schemas, Epic 6 UI schemas).**

## 6. Pre-Start Notes for Epic 4

These notes are for the **dev agent** implementing Epic 4 stories. Read before
picking up any Story 4.x.

### Critical: CacheHolder read contract

Epic 4 workers must read the cache as a **single atomic snapshot** at the top of
each dispatch cycle:

```python
# CORRECT — one snapshot per dispatch, consistent throughout
cache = CacheHolder.current          # one read → frozen RuleCache
rules = cache.rules
sources = cache.sources

# WRONG — two reads may observe different snapshots if a refresh fires between them
rules = CacheHolder.current.rules
sources = CacheHolder.current.sources  # ← may be from a newer snapshot
```

### Cache empty at startup

`CacheHolder.current` starts as `RuleCache(version=0, rules=[])`. Epic 4 workers
must handle an empty `rules` list without raising — the pipeline should no-op and
wait for the first cache refresh (30 seconds by default, configurable via
`Settings.hot_reload_interval`).

### CompiledPatterns access

`cache.compiled_patterns` is `dict[forwarding_rule_id, CompiledPatterns]`.
A rule not in this dict has no compiled patterns (literal mode, no regex).
Always use `.get(rule_id)` — never `[]` access directly.

```python
cp = cache.compiled_patterns.get(rule.id)
if cp and cp.block_patterns:
    # apply regex block filter
```

### message_mappings index pre-created

Story 3.3 pre-created the `message_mappings` compound index in `app.py`.
Story 4.1 does **not** need to create it again — only insert documents.

### Replacement rules in cache

`cache.replacements` is `dict[forwarding_rule_id, list[ReplacementRule]]`.
The list is already sorted `created_at ASC, _id ASC` (pipeline application order, FR-7).
Apply in-order — do NOT re-sort.

### `forwarding_rule_id` is a plain string

Replacement rules store `forwarding_rule_id` as a plain hex string (NOT BSON ObjectId).
Do NOT cast with `ObjectId()` when filtering by this field in Epic 4 use cases.
