## Challenges & Growth Areas

### 1. Config Naming Inconsistency (Stories 1.1 → 1.2)
The story spec referenced `settings.py` but the architecture expected `config.py`. Story 1.2 created `config.py` and deprecated `settings.py` as a backward-compatibility wrapper — leaving two files for one concern.

**Root cause:** Story spec and architecture document were not in sync on this naming.

### 2. Hardcoded Values Appeared in 3 of 4 Stories
Hardcoded ports (8000), CORS origins, and host paths showed up in Stories 1.1, 1.3, and 1.4 as code review findings. Same category of bug, multiple occurrences.

**Root cause:** "Everything configurable" was not an explicit checklist item in the dev prompt.

### 3. Story 1.3 Frontmatter Status Inconsistency
Story 1.3's frontmatter has `status: 'review'` but the body content and task checklist indicate `done`. This metadata drift can cause sprint tracking confusion.

**Root cause:** Story status was updated in the body but the frontmatter wasn't synced at close.

### 4. Windows vs. Linux Development Tension
Signal handling (SIGINT/SIGTERM) behaves differently on Windows. Story 1.1 had a review finding specifically for Windows SIGINT compatibility. The project develops on Windows but deploys to Linux — this tension will surface again.

**Root cause:** No explicit development environment stance documented.

### 5. Heavy Mocking in Test Suite
The E2E suite is comprehensive but mock-heavy. All Telegram and MongoDB calls are mocked. This is correct for unit speed, but integration tests against real services have no strategy yet.

**Root cause:** Acceptable for Epic 1 (no real business logic), but must be addressed before Epic 4's live worker.

---

## Key Insights & Learnings

1. **Code review is the quality engine** — Invest in the checklist, not just the review step. A per-story checklist item prevents the same class of bug recurring.

2. **Spec/architecture sync matters from day one** — The `settings.py` vs `config.py` ambiguity shows that mismatches between planning artifacts and implementation specs create real implementation friction. Review both before starting each story.

3. **Deferred items need owners** — A deferred-work entry without an assigned owner and target story is a wish list item. Assign them.

4. **The foundation is paying off** — Clean Architecture enforced, serialization patterns set, Docker working. Epic 2 starts from strength.

5. **Psychological safety enabled honest reviews** — The team surfaced a dead lifespan function, a shadowed variable, and other non-obvious bugs because the review process was blame-free and specific.
