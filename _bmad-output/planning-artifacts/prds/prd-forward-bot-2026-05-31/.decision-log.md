## 2026-05-31 — Consolidated gap-fill (Q1: REST API auth in MVP)

- **Decision:** Defense-in-depth. The API binds to `127.0.0.1` by default; remote access is the operator's responsibility (SSH tunnel, reverse proxy). Additionally, every protected endpoint requires a static API key supplied via `X-API-Key` header. Key is read from environment variable; rotation is a config/restart operation in MVP. Reflected in FR-API-1 and §5 Constraints (Security).
- **Rationale:** Brief defers full auth/RBAC to future scope, but operator-facing mutation endpoints (create/delete forwarding rules) cannot ship unguarded. Two cheap layers — bind address + shared secret — neutralize the obvious risk without requiring user accounts or session management in MVP.

## 2026-05-31 — Consolidated gap-fill (Q2: Hot-reload mechanism)

- **Decision:** Worker periodically refreshes the in-memory rule cache from MongoDB. Default interval **30 seconds**, configurable via env var. Maximum acceptable staleness budget: **60 seconds end-to-end** (worst case = full interval + a refresh in-flight). Reflected in FR-12 and NFR-Perf.
- **Rationale:** User chose periodic refresh over change streams / event bus. Simpler operationally, no extra infra, predictable failure mode. Trade-off accepted: rule changes are not real-time — explicit `[NOTE FOR PM]` if operators report the lag is felt.

## 2026-05-31 — Consolidated gap-fill (Q3: Source-destination cardinality)

- **Decision:** **N:N arbitrary mapping**. Each (source_channel, destination_channel) pair is a distinct row in `forwarding_rules` with its own filter/transform/media config. A single source message may trigger multiple forwards (one per matched active rule); a single destination may receive from multiple sources. Reflected throughout §4.4 and §4.5.
- **Rationale:** N:N is a superset that satisfies fan-out, aggregator, and 1:1 patterns from a single data model — no schema migration required when usage shifts.

## 2026-05-31 — Consolidated gap-fill (Q4: Telegram message semantics in MVP)

- **Decision IN scope for MVP:** Forward edits (when source message is edited, edit the forwarded copy) and propagate deletes (when source message is deleted, delete the forwarded copy). Requires persisted source→destination message-ID mapping (new MongoDB collection: `message_mappings`).
- **Decision OUT of scope for MVP:** Media albums (grouped media forwarded as N individual messages, accepted limitation) and channel service messages (joins, pins, renames — skipped entirely). Both deferred to v2 with `[NOTE FOR PM]` callouts.
- **Rationale:** Edits and deletes are common authoring behavior in real channels; missing them produces visibly out-of-sync mirrors which undermines the product's value proposition. Albums and service messages are infrequent and visually tolerable as gaps in MVP.
- **Schema delta from brief:** `message_mappings` collection added — fields recorded in PRD §4.8 and addendum data-model section.
