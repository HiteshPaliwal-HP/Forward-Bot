## 2026-05-31 — Consolidated gap-fill (Q1: REST API auth in MVP)

- **Decision:** Defense-in-depth. The API binds to `127.0.0.1` by default; remote access is the operator's responsibility (SSH tunnel, reverse proxy). Additionally, every protected endpoint requires a static API key supplied via `X-API-Key` header. Key is read from environment variable; rotation is a config/restart operation in MVP. Reflected in FR-API-1 and §5 Constraints (Security).
- **Rationale:** Brief defers full auth/RBAC to future scope, but operator-facing mutation endpoints (create/delete forwarding rules) cannot ship unguarded. Two cheap layers — bind address + shared secret — neutralize the obvious risk without requiring user accounts or session management in MVP.

## 2026-05-31 — Consolidated gap-fill (Q2: Hot-reload mechanism)

- **Decision:** Worker periodically refreshes the in-memory rule cache from MongoDB. Default interval **30 seconds**, configurable via env var. Maximum acceptable staleness budget: **60 seconds end-to-end** (worst case = full interval + a refresh in-flight). Reflected in FR-12 and NFR-Perf.
- **Rationale:** User chose periodic refresh over change streams / event bus. Simpler operationally, no extra infra, predictable failure mode. Trade-off accepted: rule changes are not real-time — explicit `[NOTE FOR PM]` if operators report the lag is felt.

## 2026-05-31 — Consolidated gap-fill (Q3: Source-destination cardinality)

- **Decision:** **N:N arbitrary mapping**. Each (source_channel, destination_channel) pair is a distinct row in `forwarding_rules` with its own filter/transform/media config. A single source message may trigger multiple forwards (one per matched active rule); a single destination may receive from multiple sources. Reflected throughout §4.4 and §4.5.
- **Rationale:** N:N is a superset that satisfies fan-out, aggregator, and 1:1 patterns from a single data model — no schema migration required when usage shifts.

## 2026-05-31 — Consolidated gap-fill (Q4: Telegram message semantics in MVP)

- **Decision IN scope for MVP:** Forward edits (when source message is edited, edit the forwarded copy) and propagate deletes (when source message is deleted, delete the forwarded copy). Requires persisted source→destination message-ID mapping (new MongoDB collection: `message_mappings`).
- **Decision OUT of scope for MVP:** Media albums (grouped media forwarded as N individual messages, accepted limitation) and channel service messages (joins, pins, renames — skipped entirely). Both deferred to v2 with `[NOTE FOR PM]` callouts.
- **Rationale:** Edits and deletes are common authoring behavior in real channels; missing them produces visibly out-of-sync mirrors which undermines the product's value proposition. Albums and service messages are infrequent and visually tolerable as gaps in MVP.
- **Schema delta from brief:** `message_mappings` collection added — fields recorded in PRD §4.8 and addendum data-model section.

## 2026-09-06 — OQ-14 and OQ-15 Resolved (Telegram Session Management)

**OQ-14 (OQ-SessionMgmt-PhoneSource). Closed.**
- **Decision:** If `TELEGRAM_PHONE` is absent from the environment, the operator enters the phone number directly in the "Connect Telegram" UI card in **E.164 format** (leading `+`, country code, number — e.g. `+919876543210`).
- **Backend behavior:** `GET /api/v1/telegram/auth/status` returns `"phone_required": true` when the env var is absent. `POST /api/v1/telegram/auth/start` accepts `{ "phone": "+..." }` in the request body; the env var takes precedence if set. Backend validates format against `^\+[1-9]\d{6,14}$`; invalid format → HTTP 422. The phone is used for that auth attempt only and is **not** written to `.env` automatically.
- **Rationale:** The operator may not have persistent shell access to the server (e.g. cloud console), or may be adding a second phone after initial deploy. Blocking auth at startup for a missing env var is too strict. Manual `.env` persistence is the operator's responsibility; documenting this in the Settings card is sufficient.
- **PRD impact:** FR-46 and FR-47 updated; `/start` API contract updated; assumption updated; OQ-14 closed in §14.

**OQ-15 (OQ-SessionMgmt-WorkerPause). Closed.**
- **Decision:** **DROP** — events arriving after `TelegramClientHolder.terminate()` sets `_connected = False` are discarded immediately (not queued).
- **Rationale:** Consistent with FR-2's established behavior during a network blip — the system never buffers; it logs and moves on. Adding a queue would require a bounded backlog, overflow policy, and replay semantics, all of which are explicitly out of scope (§7.3 — no persistent dead-letter queue in MVP). The operator is expected to re-authenticate quickly; the reconnect path (FR-47) restores normal event handling.
- **Observability:** Each drop is logged as `telegram_session_terminated_drop` with `source_message_id` and `rule_id` so the operator can see exactly what was missed.
- **PRD impact:** FR-49 (terminate consequences) and FR-51 (`_connected` flag behavior) updated; OQ-15 closed in §14.

**All Open Questions in §14 are now Closed.** PRD is ready for re-finalization and downstream skill routing.

## 2026-09-06 — Immediate DB Mutation & Manual UI Cache Refresh Enhancement

- **Trigger:** User requested `/bmad-prd` update to add immediate cache refresh on DB mutations, a manual "Refresh Cache" option in the UI, while maintaining the periodic 30-second background reload as a fallback.
- **Decision:**
  1. **Event-driven instant cache refresh on DB operations:** Any REST API mutation (Create/Update/Delete rule, replacement rule, source, folder, enable/disable rule) immediately triggers `build_rule_cache` and updates `CacheHolder.current` in-memory. Latency of config changes drops from up to 30s to <1s.
  2. **Manual UI Cache Refresh option:** Expose `POST /api/v1/admin/cache/refresh` (or `/api/v1/cache/refresh`) endpoint and add a "Refresh Cache" action button on the Web Admin Dashboard (Settings screen S8 and top navigation bar), giving the operator an on-demand escape hatch if cache state drifts.
  3. **Periodic fallback reload retained:** The background `HOT_RELOAD_INTERVAL` (default: 30s) continues to run as a safety net / fallback safeguard to ensure eventual consistency if an out-of-band DB mutation occurs or an event trigger fails.
- **Rationale:** Ensures zero-latency propagation of configuration changes during active editing, provides explicit manual operator control via UI, and preserves background polling resilience.
- **PRD Impact:** Glossary §3 updated; FR-12 expanded into FR-12a (event-driven), FR-12b (manual UI endpoint), FR-12c (periodic fallback); API Surface §9 updated; UI requirements (§4.14 / Settings S8) updated; Assumptions §13 updated.
